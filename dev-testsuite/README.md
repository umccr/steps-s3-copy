# Test suite

## Setup

All testing expects the user's current directory is
the `dev-testsuite` directory.

Requires bun >= 1.3.5 installed externally (via brew etc).

```
bun install --frozen-lockfile
```

We have chosen to pivot testing to Bun as a runtime - in anticipation
of moving the rest of the stack over to Bun at some point. Bun makes the
setup all easier as it can directly execute Typescript and has a
built-in test runner.

## Unit tests

A collection of unit(ish) tests that exercise a single stage of the Steps ASL using
the AWS Test State API thereby executing the _actual_ lambdas that are
deployed.

NOTE: THESE TESTS RUN AGAINST A _DEPLOYED_ INSTANCE - they do not run against
the local code base. However, unlike the end-to-end testing - they do not actually
invoke an orchestration, and test just a single step directly.

| Test                       |
| -------------------------- |
| `bun step-all` (all tests) |
| `bun step-can-write`       |
| `bun step-head-objects`    |

THOUGHTS: This was an attempt to utilise the AWS provided Test State API. It
offers _some_ useful features in that it exercises the code in AWS and hence
does not require mocking of S3 etc. However it is a bit unwieldy to use - because
it requires testing the raw ASL, which is text that we do not construct manually
(because we use CDK constructs). So we fetch the ASL direct from the deployed
state machine using some possibly overly convoluted mechanisms. It is possible
this would all be better as some actual unit tests in each lambda.

## End-to-end tests

A collection of tests that exercise full end to end functionality. These can be run in
any AWS account with Steps installed - and will attempt to detect configuration/settings
by looking up the installed CloudFormation.

These tests will establish a source or destination (per test) folder in the working
bucket and copy from one to the other. The test objects should expire after 1 day
(using lifecycle rules in a folder called "1day/").

| Test                | Time Est | Rationale                                                                                              |
| ------------------- | -------- | ------------------------------------------------------------------------------------------------------ |
| `bun e2e-dryrun`    | < 1min   | Creates a few files and executes in dryrun mode (does no actual copying)                               |
| `bun e2e-thawing`   | hours    | Creates a variety of sized files in cold storage and restore/copies them                               |
| `bun e2e-koalas`    | < 5min   | Copies some external data (AWS OpenData koala genomes)                                                 |
| `bun e2e-realistic` | < 5min   | Generates a realistic set of files and copies them including wildcards                                 |
| `bun e2e-report`    | < 2min   | Generates a set of files and creates the copy and estimation html reports                              |
| `bun e2e-ceph`      | < 10min  | Generates a realistic set of files and copies from S3 to the UniMelb Ceph endpoint using an AWS secret |

### S3 compatible test configuration

The `e2e-ceph` test defaults to the UniMelb Ceph endpoint and bucket. This can be changed to test a different
S3 compatible endpoint using the following envs:

| Variable                  | Default                                  |
| ------------------------- | ---------------------------------------- |
| `STEPS_TEST_ENDPOINT_URL` | `https://objects.storage.unimelb.edu.au` |
| `STEPS_TEST_SECRET_NAME`  | `ceph-5690-guardians-dev`                |
| `STEPS_TEST_BUCKET`       | `5690-guardians-dev`                     |
| `STEPS_TEST_REGION`       | `ap-southeast-2`                         |

## Local HTML Report Preview

The HTML reports are generated by `createHtmlReport()` defined in `packages/steps-s3-copy/lambda/summarise-copy-lambda/create-html-report.ts` and used by the `summarise-copy Lambda` (`summarise-copy-lambda/summarise-copy-lambda.ts`). The report can be build locally using using the mock data defined in the test script (`test-report-preview.ts`). The test will generate the report without needing to run the full workflow. There are 2 types of report, one for the actual copy and another for the dry-run, cost estimation report . To run both variants:

```bash
bun report-preview
bun report-preview-dryrun
```

These will generate `test-report-preview-copy.html`and `test-report-preview-dryrun.html` in the `dev-testsuite/` directory, respectively, and then attempt to open them in your browser (best-effort).

Note: The first time you run these commands, if there’s no `pricing-data.json` file yet, the script will grab the latest AWS pricing data for you and save it locally. Next time you run it, it’ll use the saved file.

## Cost Estimation Test

The cost estimation models can be tested directly using a set of copy scenarios (covering different file sizes, storage classes, regions, etc.) run through the actual cost calculation functions, with live AWS pricing data (fetched on first run and then cached). Results are displayed as a summary table in the terminal.

```bash
bun test-cost-estimation
```

To avoid hitting AWS Pricing rate limits, we applies a small client-side throttle and retry/backoff when fetching pricing data (see `packages/steps-s3-copy/lambda/common/cost-estimation.ts`):

```ts
const pricingThrottle = pThrottle({ limit: 5, interval: 1000 });

const PRICING_MAX_RETRIES = 5;
const PRICING_RETRY_BASE_DELAY_MS = 200;
const PRICING_RETRY_MAX_DELAY_MS = 5000;
```

The `pricing-api-fetch-throttling` script repeatedly runs the pricing fetches to exercise that throttle and the retry logic. The number of runs is controlled by the `REPEATS` variable inside the script. Per-run summaries print to stdout; retry and error diagnostics are written to stderr so you can inspect throttling activity separately.

```bash
bun pricing-api-fetch-throttling
```
